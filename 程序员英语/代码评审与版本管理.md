# 代码评审与版本管理

返回 [[程序员英语/README|程序员英语]]

### 提交与分支

- **表达**：`create a branch`（创建分支）；`commit the changes`（提交改动）；`push the branch`（推送分支）
> [!example]
> I'll commit the changes and push the branch after the tests pass.（测试通过后，我会提交改动并推送分支。）
- **提示**：`commit` 是提交到版本库，`push` 是推送到远端，含义不同。

### 发起评审

- **表达**：`open a pull request` / `open a PR`（发起拉取请求）；`request a review`（请求评审）；`This PR adds ...`（这个 PR 增加了……）
> [!example]
> I've opened a PR for the new search filter. Could you take a look?（我为新的搜索筛选功能发了 PR。能看一下吗？）

### 给出具体反馈

- **表达**：`Could we simplify this?`（这里能简化吗？）；`What happens if ...?`（如果……会怎样？）；`nit:`（小建议：）
> [!example]
> What happens if the request fails? Could we show an error message here?（如果请求失败会怎样？这里能显示错误提示吗？）
- **提示**：`nit` 是不影响主要逻辑的小意见，不适合标记必须修复的问题。

### 回复评审意见

- **表达**：`Good catch.`（发现得好）；`I've addressed your comments.`（我已处理你的评审意见）；`I left a reply with more context.`（我补充回复了背景）
> [!example]
> Good catch. I've added a test for that case.（发现得好。我已经为那个情况加了测试。）

### 合并冲突

- **表达**：`resolve a merge conflict`（解决合并冲突）；`merge the PR`（合并 PR）
> [!example]
> I need to resolve a merge conflict before we can merge the PR.（合并这个 PR 前，我需要先解决合并冲突。）

### 写清 PR 内容

- **表达**：`summary of changes`（改动摘要）；`how to test`（测试方法）；`screenshots of the UI`（界面截图）
> [!example]
> I added a summary, test steps, and screenshots to the PR description.（我在 PR 描述里补充了改动摘要、测试步骤和截图。）

### 标记未完成的工作

- **表达**：`draft PR`（草稿 PR）；`work in progress` / `WIP`（仍在进行中）；`ready for review`（可以评审）
> [!example]
> I've opened a draft PR for early feedback. It's not ready to merge yet.（我开了一个草稿 PR 征求早期意见；目前还不能合并。）

### 讨论可读性与维护

- **表达**：`This is hard to follow.`（这里不太容易理解）；`Could we give this a clearer name?`（能起个更清楚的名字吗？）；`extract a helper`（提取辅助函数）
> [!example]
> Could we give this variable a clearer name? It's hard to tell what it represents.（能给这个变量起个更清楚的名字吗？目前不容易看出它代表什么。）

### 解释自己的选择

- **表达**：`I chose this approach because ...`（我选这个方案是因为……）；`I considered ..., but ...`（我考虑过……，但……）；`I'm open to changing it.`（我愿意调整）
> [!example]
> I considered extracting a shared component, but there's only one use case so far. I'm open to changing it later.（我考虑过抽成共享组件，但目前只有一个使用场景；以后可以调整。）

### 跟进评审

- **表达**：`Could you review this today?`（今天能评审一下吗？）；`This is blocking the release.`（这件事卡住发布了）；`No rush.`（不着急）
> [!example]
> Could you review this today? It's blocking the release, and I've added test steps to the PR.（今天能评审一下吗？它卡住发布了，我已在 PR 里写好测试步骤。）
- **提示**：有截止时间时明确说明原因；`No rush` 只在确实不紧急时使用。

### 处理版本历史

- **表达**：`rebase onto the latest main`（基于最新主分支变基）；`cherry-pick a commit`（挑选某个提交应用到别的分支）；`revert a commit`（用新提交撤销旧提交）
> [!example]
> We can cherry-pick the fix into the release branch without merging the other changes.（我们可以只把修复提交挑到发布分支，不合并其他改动。）
- **提示**：`revert` 通常保留历史并新增一个反向提交；它和重写提交历史不是一回事。

### 合并后的确认

- **表达**：`The PR has been merged.`（PR 已合并）；`The change hasn't been deployed yet.`（改动尚未部署）；`I'll verify it after deployment.`（部署后我会验证）
> [!example]
> The PR has been merged, but the change won't be live until the next deployment.（PR 已合并，但下次部署前改动不会上线。）
