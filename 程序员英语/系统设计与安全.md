# 系统设计与安全

返回 [[程序员英语/README|程序员英语]]

### 讨论架构

- **表达**：`split the service into smaller parts`（将服务拆成更小的部分）；`reduce coupling`（降低耦合）；`scale the system`（扩展系统容量）
> [!example]
> We can reduce coupling by moving notifications into a separate service.（我们可以把通知移到独立服务中，以降低耦合。）
- **提示**：架构讨论要说明具体约束，不必为了“可扩展”而默认拆分服务。

### 识别瓶颈

- **表达**：`identify the bottleneck`（找出瓶颈）；`handle more traffic`（承受更多流量）；`cache frequently requested data`（缓存频繁请求的数据）
> [!example]
> Let's identify the bottleneck before adding a cache.（先找出瓶颈，再决定是否加缓存。）

### 认证与授权

- **表达**：`authenticate a user`（验证用户身份）；`authorize access`（授权访问）；`check permissions`（检查权限）
> [!example]
> The API authenticates the user and checks permissions before returning the data.（接口先验证用户身份并检查权限，然后才返回数据。）
- **提示**：`authentication` 解决“你是谁”，`authorization` 解决“你能做什么”。

### 保护敏感数据

- **表达**：`encrypt sensitive data`（加密敏感数据）；`rotate a secret`（轮换密钥）；`avoid exposing credentials`（避免泄露凭据）
> [!example]
> We should avoid exposing credentials in logs and rotate the secret if it has leaked.（我们应避免在日志中暴露凭据；若已泄露，就要轮换密钥。）

### 明确设计约束

- **表达**：`What are the constraints?`（有哪些约束？）；`How much traffic do we expect?`（预计有多少流量？）；`What matters most here?`（这里最重要的是什么？）
> [!example]
> Before choosing a design, let's clarify the expected traffic and the latency requirements.（选方案前，先确认预期流量和延迟要求。）

### 比较方案

- **表达**：`The simpler option is ...`（更简单的方案是……）；`The downside is ...`（不足之处是……）；`We can revisit this later.`（以后可以再调整）
> [!example]
> The simpler option is to keep one service. The downside is that scaling it independently will be harder.（更简单的方案是保留一个服务；不足是以后难以单独扩展其中一部分。）

### 可用性与故障

- **表达**：`single point of failure`（单点故障）；`fail over to ...`（故障时切换到……）；`graceful degradation`（降级后仍维持核心功能）
> [!example]
> If recommendations are unavailable, the product page should still load. That's a form of graceful degradation.（即使推荐服务不可用，商品页也应能打开；这是一种降级处理。）

### 限流与滥用防护

- **表达**：`rate limit requests`（限制请求频率）；`reject excessive traffic`（拒绝过量流量）；`prevent abuse`（防止滥用）
> [!example]
> We should rate limit login attempts to help prevent abuse.（我们应该限制登录尝试频率，以帮助防止滥用。）

### 输入与边界

- **表达**：`validate untrusted input`（校验不可信输入）；`sanitize user-provided content`（净化用户提供的内容）；`escape output`（转义输出）
> [!example]
> We need to validate untrusted input on the server, even if the form already checks it in the browser.（即使表单已在浏览器中校验，服务端仍需校验不可信输入。）
- **提示**：前端校验主要改善体验，不应替代服务端校验。

### 权限范围

- **表达**：`least privilege`（最小权限原则）；`grant access to ...`（授予……访问权限）；`revoke access`（撤销访问权限）
> [!example]
> The service only needs read access, so we shouldn't grant it write permissions.（服务只需要读取权限，因此不应授予写入权限。）

### 设计变更与迁移

- **表达**：`phase in the change`（分阶段引入变更）；`migrate existing users`（迁移现有用户）；`keep the old path working`（保持旧路径可用）
> [!example]
> We'll phase in the new API and keep the old endpoint working during the migration.（我们会分阶段引入新接口，并在迁移期间保持旧端点可用。）
