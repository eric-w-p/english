# 系统设计与安全

返回 [[程序员英语/README|程序员英语]]

### 讨论架构

- **表达**：`split a service`（拆分服务）；`reduce coupling`（降低耦合）；`scale the system`（扩展系统容量）
- **例句**：We could split the notification service out to reduce coupling.（我们可以把通知服务拆出来，以降低耦合。）
- **例句**：Before changing the architecture, let's check whether we actually need to scale the system.（改架构前，先确认是否真的需要扩展系统容量。）

### 识别瓶颈

- **表达**：`identify the bottleneck`（找出瓶颈）；`handle more traffic`（承受更多流量）；`cache frequently requested data`（缓存频繁请求的数据）
- **例句**：Let's identify the bottleneck before adding a cache.（先找出瓶颈，再决定是否加缓存。）
- **例句**：If the database can't handle more traffic, we could cache frequently requested data.（如果数据库承受不了更多流量，可以缓存频繁请求的数据。）

### 认证与授权

- **表达**：`authenticate a user`（验证用户身份）；`authorize access`（授权访问）；`check permissions`（检查权限）
- **例句**：The API authenticates the user before processing the request.（接口处理请求前先验证用户身份。）
- **例句**：It checks permissions to authorize access to the account data.（它检查权限，确定用户能否访问账户数据。）
- **提示**：`authentication` 解决“你是谁”，`authorization` 解决“你能做什么”。

### 保护敏感数据

- **表达**：`encrypt sensitive data`（加密敏感数据）；`rotate a secret`（轮换密钥）；`avoid exposing credentials`（避免泄露凭据）
- **例句**：We encrypt sensitive data before storing it.（我们在存储敏感数据前对其加密。）
- **例句**：Avoid exposing credentials in logs, and rotate the secret if it has leaked.（避免在日志中暴露凭据；若已泄露，就轮换密钥。）

### 明确设计约束

- **表达**：`constraints`（约束）；`expected traffic`（预期流量）；`latency requirements`（延迟要求）
- **例句**：What are the main constraints for this design?（这个设计的主要约束是什么？）
- **例句**：Before choosing an approach, let's clarify the expected traffic and latency requirements.（选方案前，先确认预期流量和延迟要求。）

### 比较方案

- **表达**：`the simpler option`（更简单的方案）；`downside`（不足之处）；`revisit later`（以后再调整）
- **例句**：The simpler option is to keep one service.（更简单的方案是保留一个服务。）
- **例句**：The downside is that scaling it independently will be harder, but we can revisit this later.（不足是以后难以单独扩展其中一部分，但之后可以再调整。）

### 可用性与故障

- **表达**：`single point of failure`（单点故障）；`fail over to`（故障时切换到）；`graceful degradation`（降级后仍维持核心功能）
- **例句**：One database instance would be a single point of failure.（只有一个数据库实例会成为单点故障。）
- **例句**：If the primary instance fails, we can fail over to a standby instance.（如果主实例故障，可以切换到备用实例。）
- **例句**：If recommendations are unavailable, the product page should still load. That's graceful degradation.（即使推荐服务不可用，商品页也应能打开；这是一种降级处理。）

### 限流与滥用防护

- **表达**：`rate limit requests`（限制请求频率）；`reject excessive traffic`（拒绝过量流量）；`prevent abuse`（防止滥用）
- **例句**：We should rate limit login attempts to help prevent abuse.（我们应该限制登录尝试频率，以帮助防止滥用。）
- **例句**：The gateway rejects excessive traffic before it reaches the service.（网关在过量流量到达服务前就会拒绝它。）

### 输入与边界

- **表达**：`validate untrusted input`（校验不可信输入）；`sanitize user-provided content`（净化用户提供的内容）；`escape output`（转义输出）
- **例句**：We need to validate untrusted input on the server, even if the browser already checks it.（即使浏览器已校验，服务端仍需校验不可信输入。）
- **例句**：Sanitize user-provided content where appropriate and escape output in the correct context.（视情况净化用户提供的内容，并根据输出位置正确转义。）
- **提示**：前端校验主要改善体验，不应替代服务端校验。

### 权限范围

- **表达**：`least privilege`（最小权限原则）；`grant access`（授予访问权限）；`revoke access`（撤销访问权限）
- **例句**：Following least privilege, we should only grant the service read access.（遵循最小权限原则，我们应该只授予这个服务读取权限。）
- **例句**：Revoke access when the integration is no longer needed.（不再需要集成时，撤销访问权限。）

### 设计变更与迁移

- **表达**：`phase in a change`（分阶段引入变更）；`migrate existing users`（迁移现有用户）；`keep the old path working`（保持旧路径可用）
- **例句**：We'll phase in the new API and keep the old endpoint working during the migration.（我们会分阶段引入新接口，并在迁移期间保持旧端点可用。）
- **例句**：We need to migrate existing users before removing the old path.（移除旧路径前，我们需要迁移现有用户。）
